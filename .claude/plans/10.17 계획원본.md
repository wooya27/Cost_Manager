# AuditFlow AI — AX/DX · 업무자동화 포트폴리오 최종 MASTER 구현 플랜

> **지원 방향:** AX/DX · AX 업무자동화 · AI Workflow Automation  
> **목표:** 기존 AuditFlow AI를 단순 Streamlit 비용관리 앱에서  
> **FastAPI · PostgreSQL · pgVector · LLM · LangGraph · Human-in-the-loop · n8n · Docker · pytest/CI · Cloud Deployment**가 실제로 연결된  
> **검증 가능하고 배포 가능한 AX / Workflow Automation 포트폴리오 프로젝트**로 확장한다.
>
> 이 프로젝트의 가치는 기술 이름의 개수가 아니라, **업무 문제를 분석하고 → 자동화 구조로 바꾸고 → 실패를 복구하고 → 결과를 저장하고 → 숫자로 평가하고 → 테스트하고 → 실제 배포하고 → 내 말로 설명할 수 있는가**로 판단한다.

# 0-0. 프로젝트를 만들게 된 배경 · 문제 정의 · 개선 방향

> 이 프로젝트의 출발점은 “AI 기술을 써보고 싶다”가 아니라, **비용 검수 업무에서 반복적으로 발생하는 확인·검색·작성·기록 작업을 줄이고, 사람이 판단해야 할 부분에 더 집중할 수 있게 만들 수 없을까?**라는 문제의식이다.

## 만들게 된 계기

비용 검수 업무는 단순히 금액만 확인하는 일이 아니다.

```text
비용 신청 확인
↓
영수증 누락 여부 확인
↓
한도 초과 여부 확인
↓
관련 규정 검색
↓
문제가 있으면 보완 요청 문구 작성
↓
승인 / 보완 / 반려 판단
↓
결과와 검수 이력 관리
```

이 과정에서 다음과 같은 불편이 발생할 수 있다.

```text
모든 건을 사람이 직접 확인해야 함
↓
정상 건과 위험 건의 우선순위가 구분되지 않음

규정을 사람이 직접 찾아야 함
↓
검색 시간이 반복적으로 발생

보완 요청 문구를 사람이 직접 작성
↓
비슷한 문구를 반복 작성

검수 결과가 여러 곳에 흩어질 수 있음
↓
누가 언제 어떤 판단을 했는지 다시 확인하기 어려움
```

## 문제 정의

```text
문제 1

문제 6
```


## 문제 → 기술 선택 이유

| 해결하려는 문제 | 선택한 방법 / 기술 |
|---|---|
| 반복적인 위험 확인 | Python 결정론적 업무 규칙 |
| 한 건에서 여러 위험이 동시에 발생 | `risks[]` 복수 위험 구조 |
| 관련 규정을 직접 찾는 문제 | Keyword Baseline + pgVector RAG |
| 반복적인 보완 문구 작성 | LLM |
| 근거 없는 AI 생성 위험 | 근거 없으면 LLM 호출 생략 → `needs_review` |
| AI가 최종 결정을 하면 안 됨 | Human-in-the-loop |
| 검사·검수 결과가 사라지면 안 됨 | PostgreSQL |
| 복잡한 상태·분기·실패 흐름 | LangGraph |
| 외부 업무도구와 반복 연결 | n8n |
| 장애 위치를 추적하기 어려움 | run_id + Logging / Observability |
| 수정 후 기존 기능이 깨질 위험 | pytest + GitHub Actions |
| 내 PC 밖에서도 사용해야 함 | Docker + Cloud Deployment |

## 데이터 파이프라인 / ETL 관점

AuditFlow AI는 AI 기능만 실행하는 프로그램이 아니라, **업무 데이터가 외부 시스템에서 들어와 검증·변환·처리·저장되고 다시 다른 시스템으로 전달되는 데이터 파이프라인**이다.

```text
[Source / Extract — 데이터 수집]
Google Sheets / Streamlit / 외부 API
↓
비용 신청 데이터 수집

[Transform — 데이터 검증·가공]
n8n
→ 입력 JSON 정리 / 필드 매핑

FastAPI + Pydantic
→ 필수 필드 / 자료형 검증

Python / Pandas
→ 업무 규칙 검사
→ risks[] 생성

pgVector RAG
→ 관련 규정 검색

LLM
→ 규정 근거 기반 보완 요청 초안 생성

[Load — 저장]
PostgreSQL
→ 검사 결과 / risks[] / policy_evidence / draft_message / review_status 저장

[Downstream — 후속 전달]
Slack
→ 위험 건 담당자 알림

Google Sheets
→ 검사 결과 다시 기록
```

### ETL과 연결하면

```text
Extract → 업무 데이터를 가져온다.
Transform → 데이터를 검증하고 업무에 필요한 형태로 바꾼다.
Load → 처리 결과를 PostgreSQL에 저장한다.
```

이 프로젝트는 전통적인 대용량 배치 ETL보다는 **API + Workflow 기반 업무 데이터 파이프라인**에 가깝다.

# 운영 원칙

- 기존 **6일 MASTER 구조는 유지**하되, 실제 구현에서는 앞 단계가 검증되지 않으면 다음 기술을 억지로 붙이지 않는다.
- Day1: 완료
- Day2~Day6: 구현 + 연결 + 실패 테스트 + 설명
- 새 기술을 많이 추가하는 것보다 **기존 흐름을 실제로 연결하고 증명하는 것**이 우선이다.
- 코드와 포트폴리오 문장이 다르면 **실제 코드와 실행 결과를 기준**으로 문서를 수정한다.
- 숫자는 반드시 직접 실행해 얻은 결과만 사용한다.
- AI 도구가 작성한 코드도 내가 **입력 → 처리 → 출력 → 실패 시 동작**을 설명하고 직접 테스트한 경우에만 프로젝트 결과로 인정한다.
- `pgVector`와 `LangGraph`는 삭제하지 않는다. 단, 핵심 위험탐지·API·DB가 검증된 뒤 연결한다.

## 모든 기능의 공통 완료 기준 — 8단계

```text
정상 실행
↓
실패
↓
복구
↓
저장
↓
평가
↓
테스트
↓
배포
↓
설명
```

### 사람 말로 보면

```text
1. 정상 실행 → 원하는 기능이 실제로 동작하는가?
2. 실패      → 일부러 오류 상황도 만들어봤는가?
3. 복구      → 오류가 나도 서비스가 어떻게 이어지는가?
4. 저장      → 결과와 검수 상태가 DB/로그에 남는가?
5. 평가      → 잘 된다는 것을 숫자로 증명했는가?
6. 테스트    → 수정 후 기존 기능이 깨지지 않는가?
7. 배포      → 내 PC 밖에서도 실행되는가?
8. 설명      → 왜 이렇게 설계했는지 코드 없이 설명 가능한가?
```

## 검증 데이터 전략

```text
초기 58건
→ 실제 버그를 발견한 진단용 데이터

500~1,000건 합성 검증 데이터
→ 정상 / 위험 / 경계값 / 복합위험 / 중복 / 이상비용을 포함한 회귀 검증

50~100개 RAG 평가 질의
→ Keyword vs pgVector Top-K 검색 성능 비교
```

- 58건은 버리지 않는다. **처음 문제를 발견한 근거**로 남긴다.
- 500~1,000건은 `seed`를 고정해 재현 가능하게 생성한다.
- RAG 평가 데이터는 비용검수 1,000건과 분리한다.

- 화면이나 호출 방식이 달라도 **핵심 업무 로직은 한 곳에 둔다.**
- 같은 위험탐지 코드를 Streamlit용 / FastAPI용으로 따로 만들지 않는다.
- 수정이 필요할 때 핵심 함수 한 곳만 바꾸면 모든 진입점에 동일하게 반영되도록 한다.

### 면접 설명

> 위험 판정은 결정론적인 업무 규칙으로 처리하고, LLM은 규정 근거를 기반으로 문장 생성에만 사용했습니다. 외부 LLM 호출이 실패해도 전체 업무가 중단되지 않도록 Template fallback을 구현했습니다.

# Day 4 — 실제 LangGraph + 장애 복구 + Observability

## 오늘 핵심 질문

> 정상일 때뿐 아니라 실패할 때도 Workflow가 제대로 움직이는가?

## Block 1 — AuditState

### 필드

```text
expense
risks                     # 복수 위험 리스트
policy_evidence           # 위험별 검색 근거
draft_message
draft_source              # llm / template / needs_review
review_status
error
run_id
```

### run_id란?

> 비용 신청 한 건의 전체 실행을 추적하기 위한 번호

## Block 2 — Node 구성

```text
audit_node
retrieve_node
generate_node
fallback_node
review_gate_node
save_node
```

### 원칙

기존 함수를 버리는 게 아니다.

```text
기존 Python 함수
↓
LangGraph Node 안에서 호출
```

### Node를 볼 때 반드시 확인할 것

```text
현재 State에 무엇이 있는가?
↓
이 Node가 어떤 값을 읽는가?
↓
무엇을 처리하는가?
↓
State의 어떤 값을 새로 쓰거나 수정하는가?
↓
다음 Node가 무엇을 받는가?
```

예시:

```text
audit_node
입력  → expense
처리  → detect_risks()
출력  → risks[]

retrieve_node
입력  → risks[]
처리  → 각 risk_reason 기준 Vector Search
출력  → 위험별 policy_evidence

generate_node
입력  → risks[] + policy_evidence
처리  → 근거가 있는 내용만 LLM 호출
출력  → draft_message, draft_source

근거 없음
→ generate_node로 보내지 않음
→ draft_source = needs_review
→ review_gate_node
→ DB에 unreviewed 상태로 저장
→ 이후 담당자가 Review API에서 최종 판단
```

### 완료 기준

- [ ] 각 Node가 읽는 State 값 설명 가능
- [ ] 각 Node가 추가/수정하는 State 값 설명 가능
- [ ] State 값이 Node 사이에서 어떻게 이동하는지 설명 가능

```text

↓

└→ save

risks[] 1개 이상
↓

└→ review_gate
   ↓

근거 있음
↓

```


## LangChain vs LangGraph — 공고 대응 이해 수준

### 아주 쉽게

```text
LangChain
→ LLM / Prompt / Retriever / Tool 같은 AI 기능을 연결하는 데 도움

LangGraph
→ 여러 AI 처리 단계의 상태와 순서, 조건 분기, 실패 경로를 관리
```

### AuditFlow에서는 왜 LangGraph인가?

```text
비용 입력
↓
위험 있음 / 없음
↓
규정 근거 있음 / 없음
↓
LLM 성공 / 실패
↓
Fallback 여부
↓
Review 필요 여부
↓
DB 저장
```

처럼 **조건에 따라 다음 단계가 달라지고 State를 계속 이어서 관리해야 하기 때문**이다.

```text
LangChain
→ AI 컴포넌트 조합 관점 이해

LangGraph
→ AuditFlow의 실제 Workflow 상태·분기 관리에 사용
```

### 목표 수준

- [ ] LangChain이 무엇을 위한 프레임워크인지 설명 가능
- [ ] LangChain과 LangGraph의 차이를 설명 가능
- [ ] AuditFlow에서 LangGraph를 선택한 이유 설명 가능
- [ ] LangChain을 억지로 추가하지 않고 필요한 경우 확장할 수 있음을 설명 가능

> 이번 프로젝트에서는 채용공고 대응을 위해 LangChain의 역할과 LangGraph와의 차이를 이해하되, 실제 Workflow 구현은 LangGraph에 집중한다.

# 최종 면접 한 문장 — 완성 후 실제 수치로 업데이트

> 현업 비용검수 프로세스를 분석해 사람이 판단해야 하는 부분과 자동화할 부분을 분리하고, FastAPI와 PostgreSQL 기반 Workflow로 구현했습니다. 초기 58건 검증에서 복수 위험이 덮어써지는 문제와 단건 API의 한계를 발견해 `risks[]`와 `/audit/batch` 구조로 개선했고, 이후 500~1,000건의 합성 검증 데이터로 회귀 테스트했습니다. 위험 건은 pgVector 기반 RAG로 규정을 검색하고 Keyword 방식과 Hit@3를 비교했으며, 근거가 없으면 LLM을 호출하지 않고 `needs_review` 상태로 DB에 저장한 뒤 담당자가 Review API에서 최종 판단하도록 설계했습니다. 조건 분기와 실패 복구는 LangGraph와 run_id 로그로 관리하고, Google Sheets → n8n → Cloud API → Slack 자동화를 실제 배포 환경에서 연결했습니다. 최종 포트폴리오에는 직접 측정한 검증 수치, 공개 Demo URL, pytest/CI 결과와 30초 E2E 영상을 함께 제시합니다.
