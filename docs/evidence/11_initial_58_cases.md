## 왜 보존하나
이 58건은 **처음 구조적 버그를 발견한 진단용 데이터**다. 버리지 않고 "문제의 출발점" 근거로 남긴다.

## 수정 전 (계획서 기록 = 당시 진단)
- 영수증 누락 **11건**이 기존 **단일 risk 구조**에서 뒤 규칙에 덮어써져 소실.
- 위험 판정 37건 중 유형/사유 **불일치 20건**.
- 중복/이상 비용 같은 **비교형 규칙**이 전체 처리 시 9건 탐지되지만 **단건 API에서는 0건**.

## 수정 후 (현재 코드로 58건 재실행 — 실측 2026-11-07)
```
총 58건 / 위험 1개 이상 탐지 35건 / 복합 위험(2개 이상) 13건

위험 유형별:
  영수증누락       19   ← has_receipt=N 19건 전부 탐지 (소실 0)
  중복 신청 의심    8   ┐ 비교형(배치 문맥) 규칙이 실제로 작동
  이상 비용 후보    8   ┘ (단건 API였다면 0건)
  식대한도 초과     8
  교통비 한도 초과   6
  택시비 사유 부족   3
  사무용품 추가 승인 3
```

## 구조 문제 해결 확인 (핵심)
| 문제 | 수정 전 | 수정 후 |
|---|---|---|
| 영수증누락 소실 | 단일 구조에서 일부 소실 | **19/19 전부 보존** (risks[] 복수 구조) |
| 비교형 규칙 | 단건 API 0건 | **배치에서 중복 8 + 이상 8 탐지** |
| 복합 위험 동시 표현 | 불가(1건당 1위험) | **13건에서 2개 이상 동시** |

> ※ "수정 전" 세부 수치는 계획서에 기록된 당시 진단값이고, "수정 후"는 동일 58건을 현재 코드로 다시 실행해 **직접 측정**한 값이다. 핵심은 개별 숫자가 아니라 **복수위험 보존·비교형 배치 탐지·복합위험 동시표현**이라는 구조적 문제가 해결됐다는 점.
